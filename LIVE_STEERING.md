# Live steering

For a short refresher with JSON examples, see [How harness replies reach the conversation](HARNESS_QUICK_REFERENCE.md).

Hive keeps one bidirectional harness process for each active conversation.
The chat box stays available while a task runs.
Messages sent during work enter that process, not a concurrent resume command.
Reviews also run serially in that conversation.
After settlement, a normal follow-up starts another turn in the same process.
An idle process normally closes after 60 seconds; a later follow-up resumes the saved session only after the previous process has been reaped.
Claude background tasks, including Monitor, keep the process alive even after its current reply finishes.
Completion of background work and completion replies restart the idle timer; active reply generation suspends idle shutdown.
Before closing an idle Claude process, Hive requests its session state and background-task snapshot and requires both to show no remaining work or pending interaction.
If the query fails or times out, Hive keeps the process alive and shows a notice instead of risking background work.
Explicit stop still closes the process.
See [Claude background-state findings](CLAUDE_BACKGROUND_STATE.md) for protocol evidence and limits.

Claude pushes background-task snapshots when work starts or finishes; the idle-time query is an extra shutdown check, not the first source of activity information.
Task cards and details show `Background work` while tasks remain, then `Preparing reply` during completion reply generation.
An alive but idle process shows neither badge.
Activity updates use the existing board polling and do not move cards, change completion timestamps, or persist stale activity across restarts.

Follow-ups leave finished cards in Results, with their original completion timestamp and an awaiting-reply indicator while work is outstanding.
The board's completion sort therefore does not promote a card when its follow-up finishes.
The explicit updated sort still uses the latest conversation activity.
Board placement is persisted separately from execution status, so task details, scheduling, cancellation, and live steering retain their existing behavior.
Follow-up failures remain visible, but do not change the card's completion position.
Retry and Continue start task work again and reset this saved placement.

Results show a New reply badge for follow-up responses not yet viewed in this browser.
The existing board poll includes the latest follow-up assistant response timestamp, derived from saved messages.
The browser stores only unread task IDs and one shared timestamp checkpoint in localStorage, not a read history for every task.
Opening the conversation in a visible tab removes its ID from that list; background tabs and the prompt tab do not mark replies read.
The first visit establishes a baseline without marking historical replies unread, and deleted task IDs are removed on the next board update.
Read tracking adds no polling or server-side read state and does not change card order.

## Supported protocols

- Pi 0.87.1 or newer, using RPC.
- Claude Code 2.1.283 or newer, with `msg_lifecycle_v1` and plural result/input associations.

Hive checks the executable version and protocol capabilities before allowing steering.
An unsupported version or missing capability produces a visible task failure rather than falling back to concurrent one-shot commands.
Wrappers must forward protocol stdin, stdout, stderr, and `--version` faithfully.
Hive owns print, mode, input/output format, and session-selection flags; remove conflicting flags from harness/template arguments.
Other model, permission, and tool arguments remain configurable.

Pi inputs use `prompt` with `streamingBehavior: steer`, which queues during work and starts a turn if the harness became idle before receiving the input.
Both Pi queue modes are explicitly set to `all`.
Hive spaces user-message writes to each Pi process by at least one second to reduce observed message loss when prompts arrive together.
The existing queue preserves submission order; the runner continues reading responses and handling control commands and cancellation during the interval.
This does not guarantee processing; see [Pi message spacing](LIMITATIONS.md#pi-message-spacing) for the evidence and limitations.
Claude inputs carry Hive-generated UUIDs.
An intermediate Claude result does not settle the conversation while other submitted UUIDs remain outstanding, even if `queued_turn_count` is zero.

## Acceptance is not an answer

`POST /api/tasks/:id/chat` returns HTTP 202 with a message ID, sequence, delivery status, and settlement flag.
The response does not contain an assistant answer.
The optional `message_id` is an idempotency key generated by the Hive client; retrying the same task, ID, and text returns its existing receipt without resending it.
Reusing an ID for different text is rejected.

Delivery states distinguish Hive acceptance, writing, harness acceptance, started delivery, inclusion in a result, rejection, failure, and uncertain delivery.
Runner states independently describe startup, active work, idle, closing, and exit.
A result can include several inputs, so one steering message does not promise one assistant response.

Pi correlates command receipts but not user or assistant events to input IDs.
Hive therefore records Pi receipt and session settlement without inventing exact per-input delivery or reply attribution.
Claude's plural result associations identify inputs included in a shared result.
Shared assistant output appears once in the conversation, not once per contributing input.
Claude results with `origin.kind: task-notification` publish background completion text without input associations and are deduplicated by result UUID.
These results do not settle outstanding user inputs; background failures also produce a visible conversation notice.
Task details expose one `messages` list instead of `prompt`, `output`, `chat_history`, `live_messages`, or separate review text.
The UI and CLI select initial answers and reviews by each message's `kind`.
See [task storage](TASK_STORAGE.md) for the schema and migration.

## Failure, cancellation, and recovery

Messages and their order are persisted before sending.
Unresolved delivery after transport loss or restart becomes unknown and is never automatically replayed.
Known unsent inputs can be marked failed instead.
The browser reuses the original message ID when retrying text after a lost HTTP response.

`hihive followup <id> "message"` sends a message to the agent (steers the agent if it is already working).
The CLI uses the same backend acceptance rules as the UI, without a separate busy check.
`--wait` waits until the submitted input settles and the conversation run finishes, then prints the latest new assistant answer.
Several inputs can share that answer; the CLI does not promise a separate reply for each message.
Failure, cancellation, or rejected or uncertain delivery makes `--wait` exit with an error.
`hihive followup <id> --cancel` requests that the active conversation run stop, including all pending messages.
It returns after the stop request is accepted, not after process cleanup finishes.
If no conversation run is active, cancellation returns an error.

Cancel stops the conversation run, including its steering inputs, rather than claiming to remove one input already incorporated into model context.
A guardian owns the harness process group and reaps its child.
Its stdin is also a liveness lease: Hive shutdown or a server crash closes the lease and terminates the harness and remaining children in that group.
Programs deliberately detached into other process groups are outside that process-group cleanup guarantee.

The runner drains stdout and stderr separately and serializes stdin writes.
Stdout EOF is an explicit controller event, not proof that the child exited.
The controller gives a still-live process a short bounded grace period, revokes its lease, and waits for cleanup.
Version checks, capability startup, input receipts, blocked writes, and shutdown have separate deadlines.

## Visible errors and durable diagnostics

Request validation errors return JSON and appear in the browser's error dialog with the draft restored.
Background protocol/process failures appear in task details and as explicit runner-stopped notices in the conversation.
Message rejection and uncertain-delivery reasons appear beside the affected input.
Unknown Claude events are recorded in diagnostics without chat warnings or changes to delivery state.
Unknown Pi events still produce a visible reduced-fidelity warning.
Required fields in events Hive consumes remain validated; malformed assistant text and invalid normal result associations are protocol errors.

The task detail API reads the latest 200 diagnostic records from the separate journal when requested.
These records are not copied into `state.json` or shown as conversation messages.
The complete append-only journal is stored beside the state file at `runner-diagnostics/<task-id>.jsonl` and survives runner shutdown and Hive restart.
Each record includes task/session/runner identity, harness, observed binary version, timestamp, order, lifecycle state, and input/result identifiers when known.
Diagnostics store redacted errors and byte counts/SHA-256 fingerprints of relevant wire/output context, not raw prompts, model output, credentials, or stderr.
Stderr fingerprints cover the retained tail, bounded to 64 KiB.
Visible runner failures include a best-effort redacted excerpt of the last eight lines of stderr (combined stdout/stderr for version-check failures), limited to 500 characters.
These excerpts are not included in the diagnostics journal, but can be saved with task errors and conversation notices.
Redaction is a precaution; we have not established that harness errors contain credentials, and redaction cannot guarantee that every secret is removed.
The ordinary conversation state still stores prompts and answers, as before.
Diagnostic write failure stops delivery and is surfaced as an error.

`HIVE_CONFIG_FILE` and `HIVE_STATE_FILE` can select isolated configuration/state paths for tests or separate Hive instances.

## Tests

The fast deterministic suite uses local fake protocol processes and does not call a model.
It requires uv and Node.js for the client tests:

```sh
./tests/run
```

Coverage includes two-message steering, shared results, active/settled races, duplicate prevention, ordinary follow-up, serialized reviews, protocol errors, lost receipts, cancellation, restart recovery, EOF while the child lives, guardian relay failure, reaping, and server SIGKILL cleanup.
API and client tests verify visible errors, redaction, and draft recovery.

The GitHub Actions Linux workflow runs only the deterministic suite.
It receives no harness credentials and does not run live tests.

Live smoke tests are explicitly opt-in and spend model tokens:

```sh
HIVE_LIVE_SMOKE=1 uv run pytest tests/test_live_smoke.py -s
HIVE_LIVE_SMOKE=1 uv run pytest tests/test_live_background.py -s
```

The background tests separately exercise Claude background Bash, Monitor completion, and explicit Monitor stop.
They use a one-second idle timeout, longer-lived background work, and a 120-second deadline per test.
The steering tests give each harness one bounded conversation with a tool gate.
The test submits two additional messages before process startup, then sends two steering messages while the tool is blocked.
It requires all four markers in the final answer, then submits two follow-ups together after settlement and checks same-process recall of the new marker and the earlier context.
Pi uses its one-second input interval; Claude receives bursts without that interval.
Each conversation has a 120-second deadline; the tool gate has a 45-second deadline.
Temporary credentials, settings, sessions, and caches are isolated under ignored `.live-smoke/` directories and removed afterward.
The tests read existing local authentication without performing a login or changing credentials.
Pi defaults to `openai-codex/gpt-6-astra`; Claude defaults to `sonnet`.
Optional overrides are `HIVE_SMOKE_PI_COMMAND`, `HIVE_SMOKE_PI_PROVIDER`, `HIVE_SMOKE_PI_MODEL`, `HIVE_SMOKE_CLAUDE_COMMAND`, and `HIVE_SMOKE_CLAUDE_MODEL`.
